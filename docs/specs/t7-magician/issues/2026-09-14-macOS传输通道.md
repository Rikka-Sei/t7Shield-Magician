# macOS 无可用 SCSI 传输通道 — Issue

**状态:** open
**发现日期:** 2026-09-14
**最后更新:** 2026-09-14（互联网深度调查追加，见 §7/§8）
**来源:** 代码/平台探测（t7Shield-protocol 仓库实测报告）；2026-09-14 互联网深度调查
**关联章节:** §4（`REQ-005 macOS 平台行为契约`、`REQ-003 传输层契约`）、§5（`TransportError::Unavailable`）、§6（降级行为）
**关联决策 ID:** D08（已归因平台降级行为）；通道选择本身未归因

## 1. 现象

在 macOS 26.6（Darwin 25.6.0，arm64）上，本机 T7 Shield（`04e8:61fc`）**没有任何用户态通道**可以把 SCSI 命令送到设备：

- `SCSITaskUserClient` 不可用：`IOServiceOpen` 返回 `0xe00002c7 (kIOReturnUnsupported)`（root 与普通用户一致）；
- 原始 USB bulk（BOT/UAS）拿不到接口：`USBInterfaceOpen` 与 `USBInterfaceOpenSeize` 均返回 `0xe00002c5 (kIOReturnExclusiveAccess)`，`kextunload -b com.apple.iokit.IOUSBMassStorageDriver` 报 `kext is in use or retained`；
- 三星私有 kext user client：`0xe00002f0 (kIOReturnNotFound)`，受 entitlement 门禁（TeamID `8S33FS7Q5Q`）；
- 唯一可用的是**只读描述符侦察**（设备描述符/配置/接口/端点），实测得到 1 配置、1 接口、2 个备用设置（alt 0 = BOT proto `0x50`、alt 1 = UAS proto `0x62`）。

> **2026-09-14 调查注记：** 「没有任何用户态通道」对**普通应用进程**（不安装驱动、不改安全策略）仍然成立；但平台并非绝对封闭——存在需要 Apple 审批（DriverKit dext）或用户主动降安全策略（kext）的合法通路，见 §7 结论矩阵。`REQ-005` 的行为契约（`TransportError::Unavailable`）不受影响。

## 3. 根因

**已确认**：Apple 按设计不允许用户态进程取得 Mass Storage 类 USB 接口，也不对 PDType = 0（磁盘）的 SCSI 设备发布 `SCSITaskUserClient`。这与权限、卷挂载状态、是否 root 都无关。

**待确认**：三条后续通道各自的实现成本与合规边界（见 §5），未做验证。

> **2026-09-14 调查注记：** §5 的「三条通道」清单已过时——深度调查（§7）发现并证实了第四条更优通路（`SCSIPeripheralsDriverKit`），并对自用 kext、三星 kext 复用给出了政策/门禁级结论。原「待确认」事项的答案见 §7 结论矩阵；spec 层面的通道选型（新决策 ID）仍留待用户拍板。

## 4. 影响

- Linux 端不受影响：`sg_io` 是内核常规能力，`REQ-004` 照常实现（B 路探测即通过 Linux 直通完成）。
- macOS 端的功能上限被锁死在「设备识别 + 描述符呈报」：解锁、口令校验都没有下发路径。
- 本 issue 不影响 `REQ-005` 的可执行性——该需求规定的行为就是「返回明确错误」，而不是「实现通道」。

## 5. 建议

三条后续通道，**需要用户拍板**后再进入 spec 与 plan（三者互不替代，成本与合规差异大）：

1. **DriverKit dext**（正规路径）：匹配 `IOUSBHostInterface` 并独占端点，在 dext 内实现 BOT/UAS。前置条件是 `com.apple.developer.driverkit.transport.usb` entitlement（需 Apple 审批），周期长；一旦落地，`Transport` trait 可直接加一个 `MacOsDext` 实现，spec 无需改结构。
2. **复用三星 kext user client**：需要另行逆向该 kext 的用户客户端协议（selector/结构体），并面对 entitlement 门禁（当前环境返回 `kIOReturnNotFound`）；合规风险最高。
3. **VM 直通中继**：客户端把命令交给一个持有 USB 直通的虚拟机（VirtualBox/UTM + Linux 客户机），由客户机执行 `sg_raw` 并回传。`tools/unlock/unlock.py` 已端到端验证该架构（宿主状态机 + 客户机传输）；代价是用户必须安装并配置虚拟机。

本 issue 与 D08 的关系：D08 只规定 macOS 的**降级行为**（可识别、盘操作返回明确错误），不预设任何通道选择；通道一旦确定，需新增决策 ID 并同步 §4/§9 与 `audit_manifest.json`。

> **2026-09-14 调查注记：** 原第 1 条「USB-interface dext + 自实现 BOT/UAS」仍可行但已非最优：调查发现 Apple 官方存在 **`SCSIPeripheralsDriverKit`**（LUN 层 dext，直接支持向 PDType 0 设备发 vendor CDB，无需自实现 BOT/UAS、无需触碰 USB 接口独占），且对「自用 kext」与「三星 kext 复用」给出了明确结论。完整矩阵见 §7.1。

## 6. 闭环记录

- open：等待用户在上述三条通道中拍板；在此之前 `REQ-005` 的行为契约有效，spec 无需变更。

**唯一/最优正路判定**：面向 MagiShield 的正式产品形态，**通路 1（SCSIPeripheralsDriverKit）是当前 Apple 生态中唯一「官方为 PDType 0 外接盘定制、不需要自实现传输协议、不触碰 USB 接口独占」的通路**；通路 2 是其保底（entitlement 明确、成本更高）。二者都需要 Apple 签发的 DriverKit entitlement + 系统扩展安装授权（`com.apple.developer.system-extension.install`），因此 **macOS 端「零安装直发 SCSI」在 2026-09 的政策下不存在**——这是对 §1 结论的收紧而非推翻。

### 7.2 A 项：DriverKit 路径逐问结论

**a) `com.apple.developer.driverkit.transport.usb` entitlement**

- 官方定义：「An array of dictionaries that identify the USB devices the driver supports.」数组每项为设备描述符字段字典，支持键：`bConfigurationValue`/`bDeviceClass`/`bDeviceProtocol`/`bDeviceSubClass`/`bInterfaceClass`/`bInterfaceNumber`/`bInterfaceProtocol`/`bInterfaceSubClass`/`bcdDevice`/`idProduct`/`idProductArray`/`idProductMask`/`idVendor`——**支持按 VID/PID 精确声明**（[S4]）。
- 申请入口：`https://developer.apple.com/contact/request/system-extension/`（需 Apple ID 登录；Apple 废弃页「Entitlements」小节同指向此表单）（[S8][S10]）。
- 实操细节（已出货 USB dext 的开发者 pmdj，Stack Overflow 高分答案）：entitlement 实际按 `idVendor`（十进制）校验；每个 VID 必须被 Apple 嵌入 provisioning profile；表单只支持单个 VID，多 VID 必须写进自由文本字段；**2022 年中起 USB transport entitlement 以通配 `*` 形式对所有开发者账号开发签名自助开放**，正式分发仍需申请（[S19]）。国内开发者亦有获批「DriverKit USB Transport - VendorID」权限的第一手记录（iPadOS 场景）（[S29]）。
- 审批口径（「给特定 USB 盘发 SCSI」类用途是否放行）：**未找到官方书面标准**。已知获批案例均为厂商自有 VID 的真实外设：DNP/Citizen 照片打印机 USB transport dext（论坛帖标题可见，[S21]）、iSCSI 厂商获批 `family.block-storage-device`（request ID `32PC8MGU57`，[S23]）。Apple 拒批「与内建驱动重复/冲突」的公开政策文本未检索到——此点标注为**未找到官方依据**，只能以 DTS 沟通确认。

**b) USB dext 能否按 VID/PID 精确匹配并取代内核 MSC 驱动对接口的占有**

- 能，且仲裁规则明确：IOKit 以 probe score 决定归属；USB 匹配有内建加分表——`idVendor+idProduct` 匹配得 90000 分，类匹配（`bInterfaceClass+SubClass+Protocol`）只有 60000 分，**精确匹配自动压过 Apple 类驱动**（[S11] QA1076 分数表）。pmdj 另证：PCI 等无内建加分表的总线需显式 `IOProbeScore`（[S20]）。
- 独占语义：dext 对 `IOUSBHostInterface` 调用 `Open()` 后取得独占；dext 匹配期间「Apple 的 mass storage 相关 kext 不再匹配该接口、文件系统不再挂载」，`Close()` 后 Apple 驱动立即接管并重新挂载（提问者实测，[S18]）。即：**dext 与内核 MSC 驱动是互斥占有，dext 凭更具体匹配赢**。
- DriverKit 侧类家族：`IOUSBHostDevice`/`IOUSBHostInterface`/`IOUSBHostPipe`（USBDriverKit，macOS 10.15+，iPadOS 亦有）。Apple 文档 DriverKit USB 支持页即 USBDriverKit 框架页（[S15]）。

**c) DriverKit 是否有 SCSI/大存储 passthrough 家族**——有，共三个（全部在 macOS 26.6 自带，[S17]）：

- **`SCSIPeripheralsDriverKit`**（DriverKit 22.0+，即 macOS 13+）：「This framework **operates at the logical unit level**」；子类 `IOUserSCSIPeripheralDeviceType00`（SBC，即 PDType 0 磁盘）/`Type05`（SMC 光驱）/`Type07`（控制器类）。核心方法 `UserSendCDB`：「Sends a vendor-specific Command Descriptor Block (CDB) to the device……deliver **vendor-specific 16-byte commands** to the external drive that this dext matches」（[S1][S2]）。SDK 头文件进一步给出：16 字节 CDB 字段（`SCSICommandDescriptorBlock`，12 字节 CDB 可用）、超时、双向缓冲与 sense 缓冲字段（[S3]）；`UserSuspendServices` 可「pause all messages to the drive from other sources……gain exclusive access to the drive」但「**The volume must be unmounted before calling this routine**」；`UserSendCDB` 头注释：vendor 命令（opcode 0xC0–0xFF）须先取得独占——本项目的 `0xA2`/`0xB5` **不在强制独占 opcode 区间**。
- **`SCSIControllerDriverKit`**（DriverKit 11.3+/macOS 11.3+）：协议层（HBA/控制器，`IOUserSCSIParallelInterfaceController`），WWDC20 发布，替代 `IOSCSIParallelFamily`（该 kext 家族 12.3 起全量废弃，[S8][S14]）。
- **`BlockStorageDeviceDriverKit`**（DriverKit 21.0+/macOS 12+）：块级，子类 `IOUserBlockStorageDevice` 把**自有协议设备呈现为块设备**（如配 PCIDriverKit），`family.block-storage-device` entitlement 明文「You must request this entitlement from Apple」（[S5][S6][S16]）。
- 注意：**没有**「向既有块设备透传任意 CDB」的家族——三个家族分别是 LUN 驱动、HBA 驱动、块设备驱动；对 MagiShield 有意义的是第一个。
- **缺口（未找到官方依据）**：官方 DriverKit entitlements 索引只列 family entitlements：audio、block-storage-device、midi、networking、scsicontroller、serial（+ transport.pci/usb + userclient 系列），**没有 scsi-peripherals 项**（[S5]）；`SCSIPeripheralsDriverKit` 文档页也未提 entitlement 要求。该家族 dext 的签名/审批门控是本次调查最大的官方信息缺口，需实测或 DTS 确认。
- 应用侧与 dext 的通信：dext 实现自定义 `IOUserClient`（官方通信模式文档/示例，[S15]）；驱动侧加 `com.apple.developer.driverkit.allow-any-userclient-access` 即允许任意应用连接（[S7]），否则用 `userclient-access` 按包 ID 白名单。应用侧只需 `com.apple.developer.system-extension.install`（容器 app 安装 dext 用）。

**d) SystemExtensions/kext vs dext 在 macOS 26 的现状**

- Apple 官方废弃页（现行有效）：「kernel extensions have been deprecated. Starting with macOS Big Sur, macOS releases **no longer load kernel extensions that use deprecated kernel programming interfaces (KPIs) by default**.」并且「Any kernel extension using an unsupported KPI **will not load**」，脚注：「Kernel extension deprecation policies are **not enforced when SIP is disabled** or if a kernel extension is **approved through a MDM profile**」（[S8]）。
- 平台安全指南 2021 版曾有「kernel extensions won't be supported on future Apple Silicon Macs」的表述（媒体存档引文，[S26]）；但截至 macOS Tahoe 26 官方用户指南仍载明 kext 的加载前置（降安全策略），即**存量支持仍在**（[S9]）；第三方厂商 2026-07 亦确认「Apple has not announced an official timeline for the removal of Kernel Extension support」（[S27]）。**未找到**「新装系统将不再支持第三方 kext」的正式官方原文——该说法目前只存在于媒体解读。

### 7.3 B 项：官方 IOKit 用户态接口全量盘查（面向「已有内核驱动的磁盘」发任意 CDB）

对 Xcode SDK（MacOSX26.sdk）IOKit 头文件做了全量枚举（本机取证），Apple 发布的所有存储相关 user client 仅：

| 接口 | 头文件 | 能否发任意 CDB | 结论 |
|---|---|---|---|
| `SCSITaskUserClient`（`kIOSCSITaskDeviceUserClientTypeID`，type 12） | `IOKit/scsi/SCSITaskLib.h` | 能（任意 CDB/sense），但头文件自我声明服务「**any SCSI Peripheral Device for which there isn't an in-kernel driver** and for **authoring devices such as CD-R/W and DVD-R/W drives**」（[S12]）；PDType 0/5/7/0xE 由 Initer `doMerge=false` 排除（[S30]） | 对本盘**不可用**（实测 0xe00002c7）；官方口径自洽 |
| MMC device user client（`kIOMMCDeviceUserClientTypeID`） | 同上 | 光驱专用（authoring devices，PDType 5） | 不适用 |
| ATA SMART user client（`kIOATASMARTUserClientTypeID`） | `IOKit/storage/ata/ATASMARTLib.h` | 仅 SMART，且以注册表 `kIOPropertySMARTCapableKey` 为门（内建 SATA 链路才发布） | 不适用 |
| NVMe SMART user client（`kIONVMeSMARTUserClientTypeID`） | `IOKit/storage/nvme/NVMeSMARTLibExternal.h` | 仅 NVMe SMART/log page | 不适用 |
| USB device/interface user client（`kIOUSBDeviceUserClientTypeID`/`kIOUSBInterfaceUserClientTypeID`） | `IOKit/usb/IOUSBLib.h` | 描述符侦察可用；接口操作被内核 MSC 驱动独占（0xe00002c5）；capture 重枚举位明文豁免 MSC 类接口：「It will not terminate any drivers attached to a Mass Storage Class IOUSBInterface」（[S13]） | 只能侦察 |

- `IOCDBDeviceAccess`、`IOSCSIUserClient`（及一切「历史变种」）：**SDK 全量 grep 零命中，不存在**（[S12] 本机取证；未找到任何官方文档提及）。
- `IOBlockStorageDevice`/`IOStorage` 家族：头文件中**无任何 user client**；BSD 层亦无 `SG_IO` 等价 ioctl。
- **smartmontools 旁证**（darwin 后端 os_darwin.cpp 全文核对）：仅实现了上述 ATA SMART 与 NVMe SMART 两条插件通道（`IOCreatePlugInInterfaceForService` + 对应 UserClientTypeID），**没有任何 SCSI/SAT/USB 透传实现**——与「macOS 无通用 CDB 通道」互为印证（[S25]）。

### 7.4 自用 kext 路径现状（macOS 26 / Apple Silicon）——回应追加问题 A

1. **加载要求**（官方步骤，[S9]）：「Before a legacy system extension (also known as a kernel extension or kext) can be installed on a Mac computer with Apple silicon, the security policy **must be changed to Reduced Security**.」具体：关机 → 长按电源键进「载入启动选项」→ Options → Recovery 里 Utilities → Startup Security Utility → Security Policy → Reduced Security → 勾选「**Allow user management of kernel extensions from identified developers**」→ 重启。
2. **自签名（非 Developer ID）kext 能否在该策略下加载**：不能。Apple 开发者论坛官方口径：「On modern systems **all KEXTs must be code signed with a Developer ID**. Additionally, **the Developer ID must be specifically enabled for KEXT development**」（[S22]）；ad-hoc/自签证书在 Apple Silicon 上被 AMFI 拒绝（社区实现普遍确认，如 macFUSE wiki 的启用步骤均以 Developer ID 为前提，[S24]）。发行另需公证。
3. **技术机制本身无限制**：kext 匹配 `IOUSBHostInterface`（VID/PID 精确匹配 90000 分压过 Apple MSC 类匹配的 60000 分，[S11]）后，以 IOKit 常规方式（自有 `IOService` 子类上发布 `IOUserClientClass`，应用 `IOServiceOpen` → `newUserClient`）向用户态暴露自定义 CDB 通道，机制成立。
4. **但政策封死默认路径**：Apple 废弃页「**USB vendor-specific IPC**」小节明文——「Any kernel extension using USB KPI (IOUSBHostFamily or IOUSBFamily) that doesn't tie into the IO Family subsystem and **uses IOUserClient, or subclasses, for IPC is unsupported in macOS Big Sur**」，且此类 kext「will not load」（[S8]）。豁免仅 SIP 关闭或 MDM。
5. **结论**：自用 kext 在 macOS 26 上是「技术上可写、政策上默认不可载」的通路；仅适合开发者本机（SIP 关闭）做协议实验，**不能作为 MagiShield 的分发形态**。列入矩阵第 4 条。

### 7.5 三星 kext 复用可行性——回应追加问题 B

- **user client 类名与协议**：`com_samsung_driver_Magician`（kext `com.samsung.magicianpssd.driver`，`/Library/Extensions/SamsungMagicianPSSDDriver.kext` 9.0.0，TeamID `8S33FS7Q5Q`）。官方守护进程 `SamsungMagicianSVC` 经由 `libSILU07.dylib` 的 `MacDriverUtility::SCSIDeviceIo` **直接 `IOServiceOpen(service, task, 0)` + `IOConnectCallMethod(selector=0, 0x50 字节结构体)`** 与内核通信——**不是 XPC**；0x50 字节结构体已完整逆向（CDB@0x18/16B、方向、sense@0x29/32B、超时@0x4c）（[S31] §4）。
- **门禁**（内核态反汇编，[S31] §5.1）：`newUserClient` 里 `IOUserClient::copyClientEntitlement` 逐条校验——无 `com.apple.application-identifier` 或 `com.apple.developer.team-identifier` → `0xe00002f0`（即本 issue 实测码）；team ≠ `8S33FS7Q5Q` 或 app id ≠ `8S33FS7Q5Q.com.samsung.magiciansvc` → `0xe00002e2`。`team-identifier` 是受限 entitlement：ad-hoc 重签携带它会被 AMFI 在 exec 阶段直接 SIGKILL（[S31] §5.2 实测错误文本）。
- **官方原件无法插桩**：hardened runtime 丢弃 `DYLD_*`；dlopen 库校验拒不同 TeamID；无 `com.apple.security.cs.debugger` 时 `task_for_pid` 被拒（[S31] §5.3）。
- **公开资料**：检索 GitHub/Reddit/通用搜索，**未找到任何第三方对 `SamsungMagicianPSSDDriver.kext` 的公开逆向分析或调用成功记录**——本仓库 `tools/interpose/README.md` 是目前可见的唯一系统性第一手分析。
- **结论**：复用不可行（第 5 条）。即使逆向出完整协议，TeamID 门禁无法以合法手段绕过。

### 7.7 「官方文档 vs 实测」矛盾点汇总

1. `IOUSBHostInterface` 文档（经 [S18] 转引）写「To use a host interface object, call Open to create a new session…」，未写明与内核类驱动的互斥仲裁；实测普通应用对被 MSC 占有的接口 `Open`/`Seize` 一律 `0xe00002c5`，而 **dext** 凭更高匹配分可以独占并使 Apple MSC 驱动完全让位（[S18][S11]）——仲裁规则只存在于 QA1076 档案与社区解读，现行 USBDriverKit 文档未写。
2. `USB.h` capture 位的「不终止 MSC 接口驱动」是**文档明文**的例外（[S13]），与实测一致——Apple 在此处口径诚实，无矛盾。
3. `SCSITaskLib.h` 自我声明「服务无内核驱动的 SCSI 外设与光驱」（[S12]）——「文档写可用」仅对磁带/扫描仪等成立；对磁盘从文档层面就已排除，与实测一致。
4. `family.scsicontroller` entitlement 文档只说「Add this entitlement」，而 `family.block-storage-device` 明文「You must request this entitlement from Apple」（[S6][S5]）——同为存储家族，措辞松紧不一，`SCSIPeripheralsDriverKit` 则完全未提；entitlement 要求的官方表述体系内部不一致。

### 7.8 对 issue 原有判断的修订说明

- **维持**：普通应用进程在 macOS 上「零安装、零审批」直发任意 CDB 的通道不存在（§1/§3 结论原样有效）；`REQ-005` 契约、D08 降级行为不变。
- **收紧/修正**：①「没有任何通道」精确化为「没有任何开箱可用通道」；②§5 原第 1 条方案被 `SCSIPeripheralsDriverKit` 通路修正（不再是唯一正规路径，且新通路实现成本更低）；③新增通路 4/5（自用 kext、三星 kext）结论：分别为「政策封死默认路径」与「门禁不可绕过」。
- **留待用户决策（不改 spec）**：若走通路 1/2，需新增决策 ID、更新 §4/§9 与 `audit_manifest.json`；通路 1 的 entitlement 未知项建议先以 DTS 工单或开发签名实测（wildcard transport.usb + LUN 匹配）确认再定稿。

## 9. 原型记录（2026-09-14，SCSIPeripheralsDriverKit dext 实测）

> 性质：调查性原型验证（§7.1 结论矩阵第 1 条通路的实证检验），非产品功能。产物：`prototype/macos-scsi-dext/`。安全红线全程遵守：唯一发出的 CDB 为 `A2 01 00 01 00 00 00 00 10 00 00 00`（Level-0 Discovery，只读）；未调用 `UserSuspendServices`；未卸载/seize 任何卷；实验前后 T7 Shield 枚举逐项一致（disk4/disk4s1 与 LUN 子树零变化）。

### 9.1 工程形态（已完整实现并编译通过）

- **dext**：`IOUserSCSIPeripheralDeviceType00` 子类 `T7DiscoveryDriver` + 自定义 `IOUserClient` 子类 `T7DiscoveryUserClient`（iig 声明，selector 0 = `SendDiscovery` LOCALONLY 方法）。User client 内创建 `IOBufferMemoryDescriptor`（数据 512B + sense 64B），填 `SCSIType00OutParameters`（16B CDB、`kSCSIDataTransfer_FromTargetToInitiator`、sense 18B、超时 30s）后调 `UserSendCDB`，响应经 `structureOutputDescriptor`/`OSData` 回宿主。
- **IOPersonality（一手 ioreg 取证确定匹配键）**：本机 T7 Shield（04e8:61fc，锁定态）的 LUN 对象实类为 `IOSCSIHierarchicalLogicalUnit`（非文档暗示的 `IOSCSIPeripheralDeviceNub`，后者是 kext 家族旧类名），LUN 属性含 `Peripheral Device Type=0`、`Vendor Identification="Samsung"`、`Product Identification="PSSD T7 Shield"`。personality 以 `IOProviderClass=IOSCSIHierarchicalLogicalUnit` + 这三个属性精确匹配，`IOProbeScore=91000`；`UserClientProperties`（`IOClass=IOUserUserClient` + `IOUserClass=T7DiscoveryUserClient`）暴露自定义 user client。基线快照：LUN 下当前客户端为三星 kext `com_samsung_driver_Magician`（`logs/baseline-lun.plist`）。
- **宿主**：`activate.m`（Objective-C，`OSSystemExtensionRequest activationRequestForExtension:queue:`，框架实名 `SystemExtensions.framework`）+ `send.c`（`IOServiceMatching("T7DiscoveryDriver")` → `IOServiceOpen` → `IOConnectCallStructMethod(selector 0)` → hexdump 前 64B 并判 0x30 处 Opal SSC 0x0203）。
- **构建（纯 clang 命令行，无 Xcode 工程）**：`iig --def X.iig --header … --impl … --deployment-target 12.0 -- -D__IIG=1 -x c++ -std=c++17 -isysroot <DriverKit.sdk>`；链接 `clang++ -target arm64-apple-driverkit23.0 -isysroot <DriverKit.sdk> -framework DriverKit -framework SCSIPeripheralsDriverKit -bundle`。命令序列见 `Makefile`。

**未执行**（激活链在宿主 entitlement 关即断，dext 从未装载）。成功判据（≥0x30 字节响应且 0x30 起解析出 Opal SSC 0x0203）留给证书就绪后的复验：`make && <用有效证书签名> && make activate && make send`。

### 9.4 失败点与定性

1. **卡点（本机级）**：无开发者账号证书 + SIP 开启（26.6 的 `systemextensionsctl developer` 工具被 SIP 硬禁）→ 装载门关死。**不是框架级否定**：`UserSendCDB` 在 2025-11 有开发者贴出成功日志（`fCompletionStatus=0x0`，Apple 论坛）；框架在 26.6 系统自带（[S17]）。
2. **技术侧已验证部分**：dext 二进制用 DriverKit SDK 命令行编译成功（93KB Mach-O bundle，含 iig 生成胶水）；`SCSIDeviceOutParameters`/`SCSIType00InParameters` 结构与填充路径走通（编译期）；LUN 匹配键以一手 ioreg 数据确定。
3. **风险提示（社区一手）**：SO 77627852（2023-12，无回答）报告该家族全部 User* 方法返回 `0xe00002c7 (kIOReturnUnsupported)`（macOS 14 时代）；其与 2025-11 成功案例的差异待复验时排查（疑似独占/匹配时序问题）。复验时若命中 2c7，先查 dext 是否已真正 attach 到 LUN（`ioreg` 子树）再查独占语义。

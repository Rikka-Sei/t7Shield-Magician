# 空应答致命判定的口径分歧（笔记 vs 参考实现） — Issue

**状态:** open
**发现日期:** 2026-09-14
**最后更新:** 2026-09-14
**来源:** 代码审计（权威笔记 与 已验证参考实现 双向比对）
**关联章节:** §4（`REQ-007 解锁事务序列`）、§5（`ProtocolError::EmptyResponse` 与「空应答」术语）、§7
**关联决策 ID:** D05

## 1. 现象

两处权威来源对「`data_len = 0` 空应答」的处置口径不一致，差别在**哪几类命令的空应答必须致命**：

| 来源 | 口径 |
|---|---|
| 权威笔记 | **SetTable 收到空应答必须判致命错**（三处明示）；同时明确「`FC`/`FA` 的空应答是正常收尾，不能据此判失败」 |
| 已验证参考实现 `tools/unlock/unlock.py` | `_expect_ok()` 对 `data_len == 0` 且无状态列表的应答**一律**记 `benign empty ack` 后 `return`，不区分命令类型；仅在报告表里把该行标为「空ack(良性)」，并在期望表中注明「SetTable ×4 … 若为 0 = 会话内命令被丢弃」 |

即：参考实现在实现上**比笔记宽松**——按当前代码，`Set` 的空应答不会中止流程，流程会继续走完并在末尾的解锁判据处失败。

## 3. 根因

两份材料的目标不同：笔记给出的是**判据规范**（把「空应答」定义为会话号错位的致命信号，并要求在 `SetTable` 上中止）；参考实现的目标是**驱动一台真实设备跑完流程并产出报告**，因此把「SCSI GOOD + 无状态列表」统一当作可继续的裸包，让流程走到末尾由解锁判据裁决，避免在诊断性 run（`--ids-mode auto|zero`）中提前中断。

**未确认**：设备在**真实会话号正确**的前提下，`Set` 是否存在合法返回空应答的情形（即宽容分支是否为必要容忍）。

## 4. 影响

- 本规格取**笔记的严格口径**并已落位：`Set` 类命令的空应答判致命（`ProtocolError::EmptyResponse`，D05），`StartTransaction` / `EndTransaction` / `EndSession` 的空应答不作为失败判据；两类结论均写入 §5。
- 该差异只影响**失败路径的表现**：严格口径会在第 N 条 `Set` 立即中止并报出步骤名；宽容口径会继续执行到判据阶段。成功路径（`data_len = 37 / 2 / 8 / 1`）两者一致，不受影响。
- 若将来设备在合法会话下出现 `Set` 空应答，严格口径会把它误报为致命——这是本 issue 需要拍板的残余风险。

## 5. 建议

需要用户拍板（三选一，均只需改 §5 与 `REQ-007` 的一处措辞 + D05 条目）：

1. **保持严格口径**（当前 spec）：`Set` 空应答即致命。优点是失败可定位到步骤；风险是合法空应答会被误判。
2. **改为宽容口径**：任何命令的空应答都不判失败，交由 §4 的成功判据裁决。好处是与已验证实现一致；代价是失败定位变弱，且与笔记的三处明示冲突。
3. **折中**：`Set` 空应答判致命，但允许在**同一次操作内**最多 1 次以「重试该条 `Set`」处理（仍由用户显式触发，不违反 D11 的零自动重放）——该折中会引入一次额外的命令下发，需新增决策 ID。

本 issue 不阻塞任何实现工作：D05 与 §5 已给出唯一权威口径。
